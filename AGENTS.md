## What this is

Browser Agent Guide is a **working Chrome Manifest V3 side-panel extension** (not a guide doc), plus a separate local Node daemon. The extension lets an LLM operate *any* web page through a **closed, deterministic verb registry** instead of free-form DOM access: the user chats in the side panel, the service worker collects page context and calls an LLM with Structured Outputs to get a fixed list of verbs + args, and the content script executes them deterministically.

The repo is **two independent npm projects** that are installed and tested separately:
- **Repo root** — the extension. Vanilla JS, ES modules, **no build step, no bundler, no linter**. The only CI is `.github/workflows/glossary.yml` (glossary checks); everything else is gated locally by `npm run check` / `make ship`.
- **`daemon/`** — a separate ESM Node service (`bag-page-feedback-daemon`) that bridges drawn-annotation screenshots from the browser to AI coding CLIs over MCP. Has its own `package.json` / `node_modules`.

UI strings are bilingual JP/EN by design (e.g. `お描き/Draw`); `README.md` is the authoritative English source and `README.ja/ko/zh.md` are translations.

## Extension architecture

Five MV3 contexts, each with a distinct job (they all share `chrome.runtime.onMessage`):

- **Service worker** (`background/service-worker.js`, `type:module`) — the orchestrator, holds no DOM. The **only** context that calls the LLM (`lib/ai-client.js`) and the only one allowed privileged APIs: `chrome.userScripts.execute`, `chrome.tabs.captureVisibleTab`, `chrome.offscreen`, `chrome.downloads`. Routes messages, auto-applies saved recipes on navigation, relays every page action to the content script.
- **Content script** (`content/content-script.js`) — a plain (non-module) IIFE injected into `<all_urls>`, guarded by `window.__AI_ADVISOR_INSTALLED__`. It **is the verb registry**: the `AI_VERBS` object (~40 verbs), the element resolver, deterministic affordance annotation (assigns stable `data-bag-id` like `button#3`), and the persistent user-annotation/drawing system. No LLM/network access of its own. `content/clipboard-hook.js` (MAIN world, `document_start`) records the page's `navigator.clipboard.writeText` text (nonce-checked) in `clipboardLog`, kept out of `COLLECT_CONTEXT`/`exportContext` (it can hold secrets and is page-controlled text) and returned only by an explicit `readSignals`.
- **Side panel** (`sidepanel/sidepanel.js`) — the chat UI. Stateless about pages; talks only to the service worker via `chrome.runtime.sendMessage`. Per-page chat/prompt history in `chrome.storage.local`.
- **Options page** (`options/options.js`) — settings editor (AI provider/key, site rules, recipes JSON, daemon). Reads/writes the single settings blob via `lib/storage.js`.
- **Offscreen document** (`offscreen/offscreen.js`) — exists **solely** because the MV3 service worker has no DOM/Canvas; it composites annotations onto screenshots with `OffscreenCanvas` + Canvas 2D. Only one offscreen doc may exist (`ensureOffscreen()` guards creation); it ignores any message where `msg.target !== 'offscreen'`.

The `lib/` modules are the "brains" — pure-ish ES modules with no global state, consumed by the service worker and offscreen doc, hence unit-testable in Node:
- `lib/ai-client.js` — provider-agnostic LLM call, **always** Structured Outputs. `'openai'` and `'custom'` share `callOpenAICompatible` (json_schema strict); `'anthropic'` forces structure via a single tool + `tool_choice`; `'gemini'` uses `responseJsonSchema` + injected `propertyOrdering`. Each provider reads a *different* model field (`ai.model` / `ai.anthropicModel` / `ai.geminiModel`).
- `lib/prompt.js` — `buildSystemPrompt` assembles the (Japanese) system prompt from the live verb catalog + page affordances/targets + human annotations + a drawing workflow, and encodes the safety/determinism policy.
- `lib/storage.js` — single settings blob under `chrome.storage.local` key `aiAdvisorSettings`. `DEFAULT_SETTINGS` is the schema source of truth; `getSettings` deep-merges defaults per sub-object.
- `lib/site-matcher.js` — pure URL matching (`all/domain/page/prefix/regex`) deciding extension + recipe activation.
- `lib/recipe-merge.js` — pure learned-recipe merge: folds newly-learned actions into an existing recipe, preserves existing hand-edited actions, carries optional `when`/`waitFor`, and dedupes on `verb+args+when+waitFor`. Consumed by `rememberPageRule` in the service worker; unit-tested by `test/recipe-merge.test.mjs`.
- `lib/judge-client.js` — System One judge client (`TypeSafe Jev`, `Cloudflare Clef` on Workers AI, or local `EmbeddingGemma 2` / `eg2`) for workflow candidate choices and post-step visual checks (`check.type === 'visual'`): builds the closed `choice` request (candidate keys + `none`; asks "same target as recorded?", which separates relabeled-same from different far better than "matches intent?") or ranks candidates via `eg2` cosine similarity, parses probabilities/scores into a closed set, and enforces https-only base URL (http only for loopback). Jev and Clef share the request/answer contract; Clef goes to a Worker proxy (`clefEndpoint`) or Workers AI REST (`clefAccountId` must be 32 hex — it lands in the URL path). Unit-tested by `test/judge-client.test.mjs` (no network).
- `lib/page-feedback/compositor.js` — Canvas-2D-only annotation compositor.

### Main chat flow (page action), end to end
1. Side panel → `CHAT{tabId,text,history,rememberScope}` to SW.
2. SW `runChat`: `getSettings` → `COLLECT_CONTEXT` to content (returns verb catalog + affordances/targets + annotations) → `buildSystemPrompt` → `callAI`.
3. SW → `RUN_ACTIONS` to content; content executes each verb deterministically in document order (with a source-based blocklist — destructive verbs are rejected on the `'chat'` path).
4. SW `rememberSuccessfulChanges` persists successful recipe verbs as a learned site rule + recipe; `syncTab`/`ACTIVATE` re-applies them once per page load — also after SPA navigation (`SPA_NAVIGATED`) and when the content script announces itself (`CONTENT_READY`, since `document_idle` injection can land after the tab finished loading). Recipe actions may carry `waitFor:{selector,timeoutMs}` / `when:{urlContains,selectorExists,selectorAbsent}`, but **only hand-edited recipe JSON can add them** (the chat Structured Outputs schema emits only `{verb,argsJson,reason}`); `lib/recipe-merge.js` keeps them across learning merges.

Page-feedback (capture): collects お描き (`kind:'drawing'`) and non-empty メモを残す (`kind:'note'`) annotations whose 「AIに渡す」 (`forAI`, default on; toggled on the drawing's memo card or per row in the side panel) is checked (`collectPageFeedbackData`). SW captures the target tab → offscreen composites → with the daemon enabled, WS push to `ws://127.0.0.1:8765/ws?token=…`; else `chrome.downloads` to `<browser download dir>/ai-inbox/<slug>/{shot.png,raw.png,annotation.json,memo.md}` (`<slug>` from `lib/slug.js`). Manual capture refuses to run when the stored target tab is no longer active (`captureVisibleTab` shoots the window's active tab). Captures record `tab:{tabId,windowId,index,active}`.

**Memo-only sync**: with `daemon.enabled`, a send set of notes only (no drawing shapes) skips the screenshot and pushes a WS payload with no `image` key, so the tab need not be active. The daemon accepts image-less payloads when `annotation` is present; the tools then advertise no `shot_url`/`file_path` and tell the model there is no image.

## Daemon architecture

One `http.Server` on one loopback port (default 8765) serves four surfaces: `/healthz` (JSON probe), `/mcp` (MCP Streamable HTTP), token-protected image GET routes `/shot/<id>.png` + `/raw/<id>.png`, and a WebSocket `upgrade` on `/ws` (extension push). The flow: extension pushes annotated PNG + metadata over WS (or a **text-only memo payload with no `image` key** — accepted when `annotation` is present; see Memo-only sync above) → `store.js` `entryStore` takes it (**default `memory`: held in RAM only, NO inbox dir created**; `disk`/`hybrid` persist `<inbox>/<slug>/` via `writer.js`) → an AI CLI POSTs to `/mcp` and first calls `get_latest_feedback_context`, getting lightweight text/structured metadata (`tab`, `@agent:`, selector, testid, anchorLabel) without image tokens. It calls `get_latest_feedback_image` only when vision is needed, passing the context `id` as `contextId` plus a concrete `imageReason`, then gets the image as MCP vision content **plus** an absolute `file_path` (the image fallback invariant). Image tools refuse to return image content when the supplied `contextId` does not match the current entry.

- `src/index.js` wires the http server (`http.js`) + WS server (`ws.js`) + token; prints MCP/WS urls + token to **stderr** (stdout stays clean). Default `storage` is **`memory`** (no inbox; `--storage`/`BAG_PF_STORAGE` → `hybrid`/`disk` to use `<inbox>/<slug>/`); on `SIGINT`/`SIGTERM` it calls `entryStore.cleanup()` to drop any `memory`-mode OS-tmp materialization.
- `src/store.js` — the `entryStore` abstraction with three modes (`normalizeStorageMode`): **`memory` (default)** keeps captures in RAM (FIFO cap 50) and, when an image/`file_path` is actually requested, materializes **to a per-process OS-tmp dir** (`mkdtemp`, dropped on `cleanup()`), so the user's `<Downloads>/ai-inbox` is **never created**; `hybrid` is the same but lazily materializes into the real `<inbox>/<slug>/`; `disk` writes eagerly on every WS push (`writeEntry`). `list_feedback`/retention/cross-restart history exist only for `disk`/`hybrid`. The two image tools' Codex⇔Claude-Code parity (no `structuredContent`) is unchanged across all modes.
- `src/http.js` — Node built-in `http`. MCP is **stateless** (a fresh `McpServer` + transport per POST, so CLIs share one endpoint). Token-protected `GET /shot/<id>.png` + `/raw/<id>.png` (constant-time compare, slug-charset ids, served from `entryStore` without touching disk). MCP text carries `shot_url`/`raw_url` **without the token on purpose** — `/mcp` is unauthenticated, so embedding the write-capable token would be a privilege escalation; the consumer appends `?token=`. URLs come only from `src/image-url.js` (shared with the `ws.js` ack). Image tools materialize `file_path` best-effort: on a disk error they still return the inline image + `shot_url` and omit `file_path`.
- `src/ws.js` — token-checked WS (constant-time; 401 + destroy on mismatch), 64MB cap; the `ack` carries token-less `shotUrl`/`rawUrl`. The socket is bidirectional: `wss.request(type, params)` sends `{type, requestId, …}` to every connected extension and resolves on the first `<type>_result` with `ok:true` (an extension that has no matching tab/memo answers `ok:false`). Used by `execute_actions` (`run_actions`) and `resolve_feedback` (`mark_annotations_done`), both handled in the SW; protocol sketch in `PROJECT.md`.
- `src/server.js` — MCP server `bag-page-feedback`: `list_feedback`, `get_latest_feedback_context`, `get_feedback_context`, `get_latest_feedback_image`, `get_feedback_image`, `evaluate_feedback_goal` (local EmbeddingGemma 2 via `src/eg2.js`; `EG2_URL`, default `http://127.0.0.1:38765`), `resolve_feedback` (marks a capture done: `resolution {at, summary}`, kept in `<slug>/resolution.json` on disk/hybrid; `get_latest_feedback_*` then answers "already handled" instead of returning it, and over WS `mark_annotations_done` the SW sets `doneAt` and unchecks 「AIに渡す」 on those memos — re-checking clears `doneAt`), `list_workflows`/`run_workflow`/`get_workflow_run`/`stop_workflow` (saved side-panel workflows over WS `workflow` `{op}`; there is deliberately no approve tool — confirm steps and judge holds wait for a person in the side panel, and `run` refuses while a run is active/held, while recording, or when the side panel has unsaved working steps), and `execute_actions` when the WS bridge is wired (always in `index.js`). Filters: `urlContains`/`titleContains` (case-insensitive substring), `tabId`/`windowId` (same-URL tabs). The image tools require `contextId` + `imageReason`, so callers cannot skip the cheap context pass.
- `src/inbox.js` / `src/writer.js` — read (newest-first scan, skips `done/`) and write (server-side slug via `src/slug.js` from `capturedAt`+`url`+`title`, tmp→rename atomic, 0600/0700, rollback on failure) sides. `inbox.js` also owns `resolveDownloadsDir()` (Win32 registry / Linux XDG / macOS `~/Downloads`) used by `defaultInboxDir()`.
- **`inboxDir` is runtime-mutable**: `index.js` holds `inboxState.dir` and passes a getter (not a string) to `http.js`/`ws.js`. When the extension reports `downloadsDir` over WS, `index.js` `adoptDownloadsDir` switches the inbox to `<downloadsDir>/ai-inbox` — UNLESS `--inbox`/`BAG_PF_INBOX` pinned it. So tests/callers may pass `inboxDir` as a string **or** a `() => dir` function.
- `src/token.js` — shared secret at `~/.bag-pf/token` (falls back to a legacy `~/.bag-vf/token` when the new path is absent); precedence flag > env > persisted file > newly generated.

## Conventions & gotchas

- **The verb registry is a CLOSED set.** The LLM can only emit verbs that exist in `AI_VERBS` (`content/content-script.js`), enforced by an enum in `buildResponseSchema` (`lib/ai-client.js`), generated from the live catalog returned by `COLLECT_CONTEXT`. Add a capability = add one verb entry; it auto-flows into both the prompt and the schema.
- **Action args travel as `argsJson` (a JSON *string*), not a nested object** — deliberately, because strict Structured Outputs requires every property required + `additionalProperties:false`, impossible for verbs with heterogeneous arg shapes. `callAI` re-parses `argsJson`. Don't try to put a typed args object in the schema.
- **`compositor.js` must stay Canvas-2D-only** — no SVG/`foreignObject`/`createElementNS`/`new Image`/`drawImage` in the module body (SVG foreignObject taints the canvas → `convertToBlob()` throws SecurityError). A banned-token scan in `compositor.test.mjs` **fails the build** if you add them. `drawImage` is allowed only in `offscreen.js` (the screenshot background).
- **Coordinates are layered**: drawings stored as 0..1 fractions of the anchored element's rect (survive reflow/scroll); at composite time `factor = dpr × outputScale` converts CSS px → output px; `computeOutputSize` caps the long edge at 2000px (vision APIs reject larger). Apply `factor` uniformly to every coordinate and line width.
- **Determinism is load-bearing**: temperature defaults to 0, affordance `aiId`s assigned in document order, recipes re-applied on revisit (and on SPA internal navigation via `SPA_NAVIGATED`→`syncTab`). Annotations persist per `origin+pathname` under `chrome.storage.local` key `aiAdvisorAnnotations`.
- **"Add note" (メモを残す) does NOT reach the daemon/MCP by itself** — it only writes `chrome.storage.local` `aiAdvisorAnnotations`. Delivery needs "Send image to AI" or `daemon.enabled` (default OFF; note-only sets then sync text-only). This is the #1 cause of "MCP says there's nothing"; empty-inbox MCP responses spell out the recovery. To recover an unsent note, use `scripts/read-annotations-cdp.mjs` (raw CDP; reads ONLY `aiAdvisorAnnotations`, never `aiAdvisorSettings`, which holds the API key) — `docs/reading-annotations-via-cdp.md`, which also explains why attach-mode `chrome-devtools-mcp` cannot see extension storage.
- **Recorded workflows are structured, deterministic steps — glossary `workflow-step` is the spec** (`lib/workflow.js` `pickCandidate`, content `runStep`, SW `driveWorkflow`; E2E `test/workflow-e2e.spec.mjs`, `test/workflow-judge.spec.mjs`). AI is only a fallback that returns one key from the candidate enum, and its pick stays a `suggestion` until the human adopts it. With `settings.judge.provider:'jev'`, `'clef'` or `'eg2'`, candidate choice and optional post-step visual verification (`check.type:'visual'`) go to System One (TypeSafe Jev, Cloudflare Clef or local EmbeddingGemma 2) with confidence gating. Invariants: (1) judge approval (`judgeApprovedStepId`) **never** releases the irreversible-click gate (`approvedStepId`); (2) an approval authorizes only the candidate the human was shown (`heldLabel` → `approvedLabel` → content `expectText`), never a re-asked AI pick; (3) neither typed step values nor live field values go to the judge/LLM chooser (for `check.type:'visual'`, `PREPARE_VISUAL_CHECK` masks live `input`/`textarea`/`contenteditable` text before `captureVisibleTab`, and refuses to shoot when the target tab is not active); (4) a judge error or malformed answer fails the step — never read it as "no match".
- **API key lives in `chrome.storage.local`, NOT `sync`** (it's a secret) — keep it that way. Always read/write settings via `lib/storage.js` so defaults merge.
- **Two recipe allow-lists must stay in sync**: `SAFE_RECIPE_VERBS` (`options/options.js`) and `RECIPE_VERBS` (`background/service-worker.js`) — both = `injectHtml/injectCss/injectScript/outlineElement/injectButton/injectPanel`. Only these get persisted and auto-replayed.
- **Security boundary**: high-risk verbs (`setStyle`, `removeElement`, `defineMarker`) are hidden from chat and rejected on chat/auto-recipe paths; page text/attributes are treated as **untrusted** (prompt-injection defense in `prompt.js`). External agents (`execute_actions`, `scripts/cdp-bridge.mjs`) get a deny-by-default allow-list — content `AGENT_ALLOWED_VERBS` = daemon `EXECUTE_ACTIONS_VERBS` (the MCP `verb` enum), parity-tested by `test/agent-verbs.test.mjs`: no `inject*`, `navigateTo`, `removeElement` or `submitForm`; `setStyle` is limited to colour/border/text/spacing/size properties with no `url()`-style external references (`agentStyleProblem`); and clicks on confirm/purchase/unnamed buttons come back `held:true` with no way to lift it. Ordinary buttons and links can still be clicked, so a click can still submit or navigate. The SW pins `source:'execute_actions'` rather than trusting the daemon's message. Don't widen verb exposure casually.
- **`injectScript` runs via the User Scripts API in the service worker**, not the content script (content sends `EXECUTE_USER_SCRIPT` to SW → `chrome.userScripts.execute`). Requires Chrome 135+ and the user manually enabling "Allow User Scripts" in `chrome://extensions`.
- **If you add a source JS file**, add it to the `check:js` file list in `package.json` (an explicit `node --check` loop — no glob). Packaging (`npm run zip` → `package-extension.sh`) uses an **exclude-list** (`zip -r . -x …`), so new source files are bundled automatically; only new dev/test/doc directories need a new `-x` exclude there.
- **Glossary = domain SSOT (`glossary/<ctx>/<id>.md`).** Before a task, read only the relevant entries and restate `id` / definition / `code_refs` / `confidence` (normalize `deprecated_terms` to the canonical name). Load-bearing code sits in `// @term: <id>` … `// @endterm` regions; when you change one, reconcile the entry and run `npm run glossary:touch <id>` — `npm run glossary:staleness` (part of `npm run check` and CI) fails otherwise. Schema, same-day exception and runbook: `docs/glossary-mechanism.md`; `glossary/TRACEABILITY.md` is generated and never committed.
- **The slug generator is DUPLICATED in two independent npm projects with no shared import**: `lib/slug.js` (extension) and `daemon/src/slug.js` (daemon) must stay **byte-identical** — `test/slug.test.mjs` imports both and fails if they drift. Folder name = `{localYYYYMMDD-HHMMSS}__{host}__{title}__{id}`; id is a **synchronous** FNV-1a hash (NOT `crypto.subtle`, which is async-only in the SW). The folder name **is** the daemon entry `id` (`inbox.js` `id: d.name`), so changing the scheme invalidates previously-emitted ids; old timestamp-named folders still list fine (scan reads arbitrary names). Embedding host/title in the name is a human/AI **skim aid only** — `annotation.json` stays the authority for `urlContains`/`titleContains` (the sanitized name is lossy, so name-matching would false-negative).
- **The `chrome.downloads` save path is the browser's download dir, NOT necessarily `~/Downloads`.** On the daemon-OFF fallback the SW resolves the real absolute path (`chrome.downloads.search`) and shows it; with the daemon ON, captures are addressed by `id` / `shot_url` (append `?token=`), so no path coordination is needed (`downloadsDir` adoption is a convenience).
- **Several test runners**: Playwright Test runs `*.spec.mjs` (`testMatch` excludes `.test.mjs`); `npm test` shells out to `playwright-cli`; root `test/*.test.mjs` are bare node scripts or `node --test` (see each `test:*` script); daemon tests use `node --test`.
- **The MCP registration alias `bag_page_feedback` is user-chosen in each CLI's config** (Claude Code/Codex key `url`, Antigravity `serverUrl`, all `http://127.0.0.1:8765/mcp`) and is not the server's internal `name`. Auth is WS-only; `/mcp` relies on loopback binding plus a Host/Origin check on every HTTP route — `/ws` relies on its token instead (DNS-rebinding defense — `execute_actions` can drive the user's tabs, so never relax it). Re-pointing a legacy `bag_visual_feedback` alias: `.agents/skills/bag-workflow/references/daemon-mcp.md`.
- **Captures carry the annotated element's HTML** (`outerHTML` ≤8KB, `truncated:true` past that) + compact a11y in `annotation.json` (`bag.page-feedback/v1`; v0 entries normalize to `null`). The context tools return them in text and `structuredContent`, so "the element I left a memo on" needs no image tokens.
- **Image MCP results must NEVER carry `structuredContent`** (Codex⇔Claude Code parity): Codex drops the entire `content[]`, image included, when `structuredContent` is present (codex#10334). The two image tools return `{content}` only — locked by `assertImageHasNoStructured` (`daemon/test/mcp.test.mjs`, `image-fallback.test.mjs`). Do NOT "fix" Codex by copying the image into `structuredContent`. The `file_path`/`shot_url` text is load-bearing for Codex (`view_image`; rmcp setup in `daemon/README.md`). The disambiguation result mirrors its warning into `structuredContent.disambiguation.message` but emits **no top-level `id`** (laundering prevention).
- **The MCP `{type:'image'}` block is a compact inline variant (~12KB WebP/JPEG), not the full PNG**: Claude Code counts image base64 as text against `MAX_MCP_OUTPUT_TOKENS` (25k) and drops the image on overflow. `offscreen/inline-encode.js` produces it (`INLINE_BYTE_BUDGET`, derivation in its header — **do not raise it toward 30KB**); `buildEntryContent` (`daemon/src/inbox.js`, the only image site) prefers it and omits the image above `INLINE_MAX_BYTES` (14KB). `file_path`/`shot_url`/downloads stay full-res PNG. `inlineMime` comes from the produced `blob.type`, never hardcoded. The lossy encode lives only in `inline-encode.js`, so `compositor.js` stays Canvas-2D-only.
- **The shared `~/Downloads/ai-inbox`** can hold other projects' captures (still pass `urlContains`/`titleContains`, and `tabId`/`windowId` for same-URL tabs):
  - **disambiguate-latest** (default ON): a bare `get_latest_feedback*` that sees ≥2 hosts within the window (`capturedAt`-anchored) returns a candidate list — no image and **no top-level `structuredContent.id`**; the image tool honors only a `contextId` from that list.
  - **retention sweep** (default OFF, `--retention on`): archives into `<inbox>/done/` by rename — never delete, never inside the grace window. **GOTCHA: `familyKey` must strip both the leading `{stamp}` and the trailing `{hash}`**, or the family cap is a silent no-op. Defaults and flags: `daemon/README.md`.
- **UI is bilingual JP/EN**; keep new user-facing strings bilingual. The anti-slop UI quality workflow (`docs/ui-quality-workflow.md`) requires generated UI changes to be backed by a repeatable Playwright/axe test or screenshot, verified at side-panel width.
- **Before shipping a long-lived worktree**, run `git fetch origin main && git diff --name-status origin/main...HEAD` and re-scope if upstream removed or rewrote files you depend on: the Stop-time staleness guard reads a never-refreshed local `origin/main`, and a small `behind` count can still hide a modify/delete conflict. `mark-pre-ship-confirmed.mjs` also warns (stderr) on same-file overlap. ## Git workflow

- **GitHub Flow** — never commit straight to `main`. Branch from `main` (`feat/…`, `fix/…`), commit, push, open a PR, then merge.
- **Commit messages in English**, imperative mood (e.g. "Add @agent: marker lint"); subject ≤ ~72 chars, body explains the *why* when non-trivial.
- **Default shipping = `make -C <worktree> ship` (all CLIs: Claude Code / Codex / Antigravity)**. When the task's work is committed in its worktree, run it instead of asking the PR question. `scripts/auto-ship.mjs` runs `npm run check` (+ daemon tests if `daemon/` changed), a read-only headless `claude -p` review, pushes and opens the PR, and — only if every gate passes — squash-merges and runs `agent-worktree-guard` `mark-merged` + `cleanup --confirmed`. The repo owner authorized auto-merge for changes that pass these gates (2026-10-08); the hooks only see `make ship`, so the script itself is the merge gate for this path. Gates that stop at an open PR (`AUTO_SHIP NEEDS_HUMAN`): size or protected paths (`MAX_FILES`/`MAX_LINES`/`PROTECTED` in `scripts/auto-ship.mjs` are the source of truth), review verdict `request_changes`, or review scope `large` (big refactor / large feature / architecture or data-format change); review failure fails closed. On `NEEDS_HUMAN` report the PR URL + reasons and fall back to the manual flow below (which then still requires the Pre-Ship panel + human confirmation before merge). On `FAILED` fix and re-run. Do not loosen the thresholds or the protected list to get a merge through.
- **Manual shipping (for `NEEDS_HUMAN`, or when the user asks to review first) goes through `gh` directly**: commit in the worktree (`git -C <wt>`); after the human agrees to a PR, run `agent-worktree-guard confirm-pr --confirmed`, then `gh pr create`. Before `gh pr merge` (irreversible), present the 7-section Pre-Ship Human Review Panel, get explicit user confirmation, and run `node .claude/scripts/mark-pre-ship-confirmed.mjs <branch> --quality <agent_go|self_review_pass|trivial_skip>`; `pre-ship-review-guard` blocks the merge until that marker is fresh (10 min). Run `gh pr merge` from the worktree **without `--delete-branch`/`-d`** (gh would fail its local `main` checkout yet exit 0 — verify with `gh pr view <n> --json state`; `merge-guard.mjs` denies the flag). The guard CLI is the wrapper `scripts/agent-worktree-guard/agent-worktree-guard` (`confirm-pr`/`mark-merged`/`cleanup`/`status`); `.claude/hooks/agent-worktree-guard.mjs` only dispatches hooks. `cleanup --confirmed` (from the main checkout) removes merged worktrees with their local + remote branches and branch-specific stashes, and reconciles ledger entries whose directory is already gone. Background: `docs/retros/` (`orphaned-ship-gate`, `ledger-entry-orphaned-from-resource-lifecycle`, `gh-pr-merge-delete-branch-from-worktree`).
- **Mandatory Post-Merge Cleanup Invariant (All CLIs: Claude Code / Codex / Antigravity)**: When a PR is merged — whether through `make ship`, manual `gh pr merge`, or via GitHub Web review — the agent is **strictly required** to ensure full cleanup of the worktree and branches before reporting task completion or ending the session:
  1. **Primary path**: For worktrees tracked by the guard, run `scripts/agent-worktree-guard/agent-worktree-guard cleanup --confirmed` from the main checkout. This safely and deterministically removes the worktree, force-deletes the merged local branch (`git branch -D`), and removes the remote branch.
  2. **Unregistered worktree fallback**: If the worktree was created outside the guard ledger, ensure the PR is merged, then bring it into the ledger and clean it the same way: `agent-worktree-guard register <path>` → `mark-merged <path>` → `cleanup --confirmed` (raw `git worktree remove` is blocked by the guard hook).
  3. **Verification**: Always sync main (`git pull --ff-only origin main`) and verify with `git branch` (or run `make clean.branches`) to confirm no stale feature/fix branches linger.
  **Reporting a successful merge while leaving the local branch behind is strictly prohibited.**
