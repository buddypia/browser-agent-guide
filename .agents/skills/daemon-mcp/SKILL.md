# Daemon & MCP

`daemon/` is a separate ESM npm project (`bag-page-feedback-daemon`, own `package.json`/`node_modules`) that bridges drawn-annotation screenshots from the browser to AI coding CLIs over MCP. Root `npm run check` does **not** cover it.

## Commands (`cd daemon` first)
```bash
npm install                      # daemon deps (@modelcontextprotocol/sdk, ws, zod)
npm start                        # node src/index.js  (default storage=memory: no inbox dir is created; port 8765, host 127.0.0.1)
npm run service -- [--write] [--port N …]  # print (or --write) a launchd/systemd unit to run the daemon persistently
npm test                         # node --test 'test/*.test.mjs'  (node:test)
node --test test/inbox.test.mjs  # single daemon test file
node scripts/e2e-smoke.mjs       # real-binary E2E: spawn daemon, WS push -> MCP get, on a temp inbox
curl -s http://127.0.0.1:8765/healthz
```
Override via flags `--inbox/--port/--host/--token` or env `BAG_PF_INBOX/BAG_PF_PORT/BAG_PF_HOST/BAG_PF_TOKEN`.

## Daemon architecture

One `http.Server` on one loopback port (default 8765) serves four surfaces: `/healthz` (JSON probe), `/mcp` (MCP Streamable HTTP), token-protected image GET routes `/shot/<id>.png` + `/raw/<id>.png`, and a WebSocket `upgrade` on `/ws` (extension push). The flow: extension pushes annotated PNG + metadata over WS (or a **text-only memo payload with no `image` key** — accepted when `annotation` is present; see Memo-only sync in the extension-architecture skill) → `store.js` `entryStore` takes it (**default `memory`: held in RAM only, NO inbox dir created**; `disk`/`hybrid` persist `<inbox>/<slug>/` via `writer.js`) → an AI CLI POSTs to `/mcp` and first calls `get_latest_feedback_context`, getting lightweight text/structured metadata (`tab`, `@agent:`, selector, testid, anchorLabel) without image tokens. It calls `get_latest_feedback_image` only when vision is needed, passing the context `id` as `contextId` plus a concrete `imageReason`, then gets the image as MCP vision content **plus** an absolute `file_path` (the image fallback invariant). Image tools refuse to return image content when the supplied `contextId` does not match the current entry.

- `src/index.js` wires the http server (`http.js`) + WS server (`ws.js`) + token; prints MCP/WS urls + token to **stderr** (stdout stays clean). Default `storage` is **`memory`** (no inbox; `--storage`/`BAG_PF_STORAGE` → `hybrid`/`disk` to use `<inbox>/<slug>/`); on `SIGINT`/`SIGTERM` it calls `entryStore.cleanup()` to drop any `memory`-mode OS-tmp materialization.
- `src/store.js` — the `entryStore` abstraction with three modes (`normalizeStorageMode`): **`memory` (default)** keeps captures in RAM (FIFO cap 50) and, when an image/`file_path` is actually requested, materializes **to a per-process OS-tmp dir** (`mkdtemp`, dropped on `cleanup()`), so the user's `<Downloads>/ai-inbox` is **never created**; `hybrid` is the same but lazily materializes into the real `<inbox>/<slug>/`; `disk` writes eagerly on every WS push (`writeEntry`). `list_feedback`/retention/cross-restart history exist only for `disk`/`hybrid`. The two image tools' Codex⇔Claude-Code parity (no `structuredContent`) is unchanged across all modes.
- `src/http.js` — Node built-in `http`. MCP is **stateless** (a fresh `McpServer` + transport per POST, so CLIs share one endpoint). Token-protected `GET /shot/<id>.png` + `/raw/<id>.png` (constant-time compare, slug-charset ids, served from `entryStore` without touching disk). MCP text carries `shot_url`/`raw_url` **without the token on purpose** — `/mcp` is unauthenticated, so embedding the write-capable token would be a privilege escalation; the consumer appends `?token=`. URLs come only from `src/image-url.js` (shared with the `ws.js` ack). Image tools materialize `file_path` best-effort: on a disk error they still return the inline image + `shot_url` and omit `file_path`.
- `src/ws.js` — token-checked WS (constant-time; 401 + destroy on mismatch), 64MB cap; the `ack` carries token-less `shotUrl`/`rawUrl`. The socket is bidirectional: `wss.request(type, params)` sends `{type, requestId, …}` to every connected extension and resolves on the first `<type>_result` with `ok:true` (an extension that has no matching tab/memo answers `ok:false`). Used by `execute_actions` (`run_actions`) and `resolve_feedback` (`mark_annotations_done`), both handled in the SW; protocol sketch in `PROJECT.md`.
- `src/server.js` — MCP server `bag-page-feedback`: `list_feedback`, `get_latest_feedback_context`, `get_feedback_context`, `get_latest_feedback_image`, `get_feedback_image`, `evaluate_feedback_goal` (local EmbeddingGemma 2 via `src/eg2.js`; `EG2_URL`, default `http://127.0.0.1:38765`), `resolve_feedback` (marks a capture done: `resolution {at, summary}`, kept in `<slug>/resolution.json` on disk/hybrid; `get_latest_feedback_*` then answers "already handled" instead of returning it, and over WS `mark_annotations_done` the SW sets `doneAt` and unchecks 「AIに渡す」 on those memos — re-checking clears `doneAt`), `list_workflows`/`run_workflow`/`get_workflow_run`/`stop_workflow` (saved side-panel workflows over WS `workflow` `{op}` — rules in the workflow-steps skill), and `execute_actions` when the WS bridge is wired (always in `index.js`). Filters: `urlContains`/`titleContains` (case-insensitive substring), `tabId`/`windowId` (same-URL tabs). The image tools require `contextId` + `imageReason`, so callers cannot skip the cheap context pass.
- `src/inbox.js` / `src/writer.js` — read (newest-first scan, skips `done/`) and write (server-side slug via `src/slug.js` from `capturedAt`+`url`+`title`, tmp→rename atomic, 0600/0700, rollback on failure) sides. `inbox.js` also owns `resolveDownloadsDir()` (Win32 registry / Linux XDG / macOS `~/Downloads`) used by `defaultInboxDir()`. `src/slug.js` must stay byte-identical to the extension's `lib/slug.js` (`npm run check:sync`).
- **`inboxDir` is runtime-mutable**: `index.js` holds `inboxState.dir` and passes a getter (not a string) to `http.js`/`ws.js`. When the extension reports `downloadsDir` over WS, `index.js` `adoptDownloadsDir` switches the inbox to `<downloadsDir>/ai-inbox` — UNLESS `--inbox`/`BAG_PF_INBOX` pinned it. So tests/callers may pass `inboxDir` as a string **or** a `() => dir` function.
- `src/token.js` — shared secret at `~/.bag-pf/token` (falls back to a legacy `~/.bag-vf/token` when the new path is absent); precedence flag > env > persisted file > newly generated.

## MCP output invariants

- **Image MCP results must NEVER carry `structuredContent`** (Codex⇔Claude Code parity): Codex drops the entire `content[]`, image included, when `structuredContent` is present (codex#10334). The two image tools return `{content}` only — locked by `assertImageHasNoStructured` (`daemon/test/mcp.test.mjs`, `image-fallback.test.mjs`). Do NOT "fix" Codex by copying the image into `structuredContent`. The `file_path`/`shot_url` text is load-bearing for Codex (`view_image`; rmcp setup in `daemon/README.md`). The disambiguation result mirrors its warning into `structuredContent.disambiguation.message` but emits **no top-level `id`** (laundering prevention).
- **The MCP `{type:'image'}` block is a compact inline variant (~12KB WebP/JPEG), not the full PNG**: Claude Code counts image base64 as text against `MAX_MCP_OUTPUT_TOKENS` (25k) and drops the image on overflow. `offscreen/inline-encode.js` produces it (`INLINE_BYTE_BUDGET`, derivation in its header — **do not raise it toward 30KB**); `buildEntryContent` (`daemon/src/inbox.js`, the only image site) prefers it and omits the image above `INLINE_MAX_BYTES` (14KB). `file_path`/`shot_url`/downloads stay full-res PNG. `inlineMime` comes from the produced `blob.type`, never hardcoded.
- **Captures carry the annotated element's HTML** (`outerHTML` ≤8KB, `truncated:true` past that) + compact a11y in `annotation.json` (`bag.page-feedback/v1`; v0 entries normalize to `null`). The context tools return them in text and `structuredContent`, so "the element I left a memo on" needs no image tokens.
- **The shared `~/Downloads/ai-inbox`** can hold other projects' captures (still pass `urlContains`/`titleContains`, and `tabId`/`windowId` for same-URL tabs):
  - **disambiguate-latest** (default ON): a bare `get_latest_feedback*` that sees ≥2 hosts within the window (`capturedAt`-anchored) returns a candidate list — no image and **no top-level `structuredContent.id`**; the image tool honors only a `contextId` from that list.
  - **retention sweep** (default OFF, `--retention on`): archives into `<inbox>/done/` by rename — never delete, never inside the grace window. **GOTCHA: `familyKey` must strip both the leading `{stamp}` and the trailing `{hash}`**, or the family cap is a silent no-op. Defaults and flags: `daemon/README.md`.
- **The MCP registration alias `bag_page_feedback` is user-chosen in each CLI's config** (Claude Code/Codex key `url`, Antigravity `serverUrl`, all `http://127.0.0.1:8765/mcp`) and is not the server's internal `name`. Auth is WS-only; `/mcp` relies on loopback binding plus a Host/Origin check on every HTTP route — `/ws` relies on its token instead (DNS-rebinding defense — `execute_actions` can drive the user's tabs, so never relax it). Re-pointing a legacy `bag_visual_feedback` alias: `.agents/skills/bag-workflow/references/daemon-mcp.md`.

## When MCP says there is no feedback

**"Add note" (メモを残す) does NOT reach the daemon/MCP by itself** — it only writes `chrome.storage.local` `aiAdvisorAnnotations`. Delivery needs "Send image to AI" or `daemon.enabled` (default OFF; note-only sets then sync text-only). This is the #1 cause of "MCP says there's nothing"; empty-inbox MCP responses spell out the recovery — relay that text to the user. To recover an unsent note, use `scripts/read-annotations-cdp.mjs` (raw CDP; reads ONLY `aiAdvisorAnnotations`, never `aiAdvisorSettings`, which holds the API key) — `docs/reading-annotations-via-cdp.md`, which also explains why attach-mode `chrome-devtools-mcp` cannot see extension storage.
